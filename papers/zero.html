ZeRO

~ memory optimization for training huge models (SC 2020) ~

Part 1 — the brilliant finding: data doesn't need to be replicated in memory for computation to be parallel. Instead of every GPU holding the entire model, each GPU holds only a 1/N shard of each layer — layer 1 shard, layer 2 shard, layer 3 shard, … Then for each layer, an all-gather reconstructs the full layer just-in-time for computation. The memory buffer needed is the size of the largest single layer, not the entire model. This is the key to breaking the ultimate bottleneck on model size.

Part 2 — domain knowledge.

2a. Parallelism strategies. DATA PARALLELISM (DP) requires every GPU to hold a full copy of the model — fine when the model fits, but breaks down as models grow huge. The fix is MODEL PARALLELISM (MP), which comes in two flavors:

  • TENSOR PARALLELISM (TP) — intra-layer splits. A single layer is split across GPUs. Enables very large layers, but every forward and backward pass requires all-reduce communication within the layer, making communication overhead the main cost.
  • PIPELINE PARALLELISM (PP) — inter-layer splits. Layers are partitioned across GPUs (GPU 1 runs layers 1–4, GPU 2 runs layers 5–8, …). Less communication, but the classic pipeline bubble problem: GPUs early in the pipeline sit idle waiting for the backward pass to arrive, wasting compute.

LLM parallelism methods at a glance (DP / TP / PP / ZeRO).

Method What is split? What each GPU stores How computation works Communication pattern Main drawback
Data Parallel (DP) Batch (data) Full model + different mini-batch Each GPU runs full forward/backward independently Gradient all-reduce each step Model must fit on one GPU; full model duplicated everywhere
Tensor Parallel (TP) Model tensors (matrix rows/columns, attention heads) Shards of weight matrices (e.g., W0, W1) + full activations Each GPU computes partial matmul outputs for each layer Frequent all-gather / all-reduce of intermediate activations per layer High communication overhead; tight synchronization inside every layer
Pipeline Parallel (PP) Model depth (layers) Different contiguous layers per GPU Micro-batches flow stage-by-stage through GPUs Activation passing between pipeline stages Pipeline bubbles (GPU idle time), limited utilization, microbatch complexity
ZeRO / FSDP (ZeRO-3) Training states (parameters, gradients, optimizer states) Sharded parameters (W0, W1, etc.) All-gather full weights per layer → full layer compute → discard/shard again All-gather parameters + reduce-scatter gradients per layer Communication overhead for parameter reconstruction; bandwidth-bound at scale

2b. Where the memory goes — model states vs. residual states. ZeRO splits GPU memory into two buckets:

  • MODEL STATES — the big, persistent consumers. Three pieces: the parameters, the gradients, and the optimizer states. For the Adam optimizer the optimizer states are the per-parameter momentum (the running mean of gradients) and variance (the running mean of squared gradients). With mixed-precision training these dominate: Adam keeps fp32 copies of the parameters, momentum, and variance, so the optimizer states alone can cost several times the size of the model itself.
  • RESIDUAL STATES — everything else: activations saved for the backward pass, temporary buffers, and fragmented (unusable) memory.

2c. ZeRO vs. tensor parallelism — both split intra-layer, so what's different? The split is of different things:

  • TP splits the computation. Each GPU permanently owns a slice of the layer and computes only its slice of the matrix multiply. The full layer is never materialized on one GPU; instead the partial results are combined with an all-reduce during every forward and backward pass. Communication is intrinsic to the math, which is why TP is bandwidth-hungry and usually kept within a single node.
  • ZeRO splits only the storage. Computation stays data-parallel — each GPU still computes the whole layer. It just doesn't keep the whole layer resident: it all-gathers the shards to rebuild the full layer right before computing, runs the full layer, then frees the gathered copy. The math each GPU does is identical to plain DP; only the memory footprint is sharded.

Example. Say one layer is a matrix multiply Y = X · W, the weight W is split into a left half W_L and a right half W_R, and we have 2 GPUs each holding one half.

  • Under TP: both GPUs see the same input X. GPU0 computes X · W_L, GPU1 computes X · W_R — each does half the multiply and produces a partial result. They then all-reduce to combine the halves into the full Y. Neither GPU ever holds all of W, and the communication is part of computing this one layer.
  • Under ZeRO: the two GPUs see different data batches (it's still data-parallel). Before computing, GPU0 all-gathers W_R from GPU1 to rebuild the full W, then computes the entire Y = X · W on its own batch; GPU1 does the same on its batch. Each GPU does the full multiply, and once the layer is done it frees the gathered W_R so memory drops back to one half.

In short: TP partitions the work (each GPU does a fraction of the layer's math, communicating mid-computation), while ZeRO partitions the memory (each GPU does the full math redundantly, communicating only to gather/scatter parameters around it).

Why ZeRO wins.

  • Cheaper, off-the-critical-path communication. TP's all-reduce sits inside every layer's forward and backward pass — compute must wait on it, so it can't easily be hidden. ZeRO keeps the data-parallel pattern (all-gather params, reduce-scatter gradients), and those gathers can be prefetched and overlapped with compute of the previous layer. Total communication volume stays close to plain DP rather than scaling with every matrix multiply.
  • Scales beyond a single node. Because TP communicates so heavily per layer, it's effectively pinned to one box with high-bandwidth NVLink. ZeRO's lighter traffic lets it shard across many nodes, so memory savings grow linearly with the number of GPUs — the path to truly huge models.
  • Drop-in, no model rewrite. TP requires surgically splitting each layer's math and inserting collectives by hand. ZeRO leaves the model code untouched — it's a transparent replacement for ordinary data-parallel training.
